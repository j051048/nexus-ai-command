## 一、来自内部代码审计的暂缓项

### 1. 招标信息实时爬虫（原第4项）
- **背景**：当前仅有 arXiv 学术爬虫，缺少真实招标网站数据源
- **所需条件**：接入中国政府采购网、各省公共资源交易中心 API
- **预估工作量**：中等
- **启动条件**：获取招标网站 API 权限或找到合适的第三方数据服务商

### 2. 金蝶ERP集成（原第5项）
- **背景**：当前为 stub 接口，需要金蝶 K3 Cloud SDK 和真实凭证
- **所需条件**：金蝶 K3 Cloud 开发者账号、API 密钥、测试环境
- **预估工作量**：中等
- **启动条件**：客户实际使用金蝶ERP时按需接入

### 3. Tool Schema 多实例同步（原第5项）
- **背景**：当前 `_tool_schema_version` 是进程内全局变量，多 Pod 部署时无法同步
- **现状**：单实例部署，不存在此问题
- **方案**：Redis pub/sub 广播工具注册变更
- **启动条件**：K8S 多副本部署时

### 4. DDD 服务层领域拆分（原第7项）
- **背景**：`app/services/` 下 60+ 文件扁平结构
- **现状**：业务快速迭代中，过早拆分增加开发成本
- **方案**：按 CRM/审批/AI引擎/身份/知识库/集成/计费 划分 Bounded Context
- **启动条件**：功能稳定后，团队扩大需要明确边界时

### 5. Canvas/Artifact 白板扩展（原第9项）
- **背景**：当前 @xyflow/react 仅用于审批流设计器
- **方案**：扩展为通用 AI Artifact 白板（类似 Claude Artifacts）
- **启动条件**：作为产品差异化功能规划，需要独立产品设计

### 6. Terraform IaC（原第10项）
- **背景**：基础设施通过 Supabase 托管 + Zeabur PaaS 管理
- **现状**：手写 K8S YAML 已够用
- **启动条件**：自建集群、多区域部署时

### 7. Chaos 混沌测试（原第11项）
- **背景**：circuit breaker 和 retry 机制已内置但未经故障注入验证
- **方案**：toxiproxy 或 mock middleware 注入 LLM 超时/限流/DB 不可用等故障
- **启动条件**：产品上生产高负载后

## 二、来自外部 OpenAI 专家建议的暂缓项

### 8. 知识资产结构化管理
- **建议来源**：IanCompany_V2 架构启发 §2.1
- **内容**：按情报库/方法论库/内容库/工作流库组织知识资产，前端增加知识看板
- **暂缓原因**：本质是前端分类 UI 工作，后端 documents 表加 `category` 字段即可，但大量前端开发投入产出比低
- **启动条件**：核心功能稳定后作为 UX 增强

### 9. 能力热力图可视化
- **建议来源**：IanCompany_V2 架构启发 §3.3
- **内容**：展示各模块（OA/财务/HR/CRM）的使用频率、成功率、满意度热力图
- **暂缓原因**：需要大量使用数据积累，当前数据量不足以支撑有意义的热力图
- **启动条件**：日活跃用户达到一定规模，累积足够的 trace 数据

### 10. 内容版本管理（草稿→审核→定稿→归档）
- **建议来源**：IanCompany_V2 架构启发 §3.4
- **内容**：AI 生成的报告/文案等增加完整版本生命周期管理
- **暂缓原因**：审批系统已有生命周期管理，对话记录天然有版本（chat_messages 表）
- **启动条件**：当 AI 内容生成成为核心业务流程时

### 11. 灵感收集 + 智能待办
- **建议来源**：IanCompany_V2 架构启发 §4.2
- **内容**：用户对话中说"记一下"自动归档为待办或灵感笔记，支持智能到期提醒
- **暂缓原因**：UX 增强功能，对核心产品价值贡献小
- **启动条件**：作为用户体验优化批次

### 12. 协作冲突处理
- **建议来源**：IanCompany_V2 架构启发 §5.2
- **内容**：多 Agent/用户同时修改同一资源时的乐观锁和冲突检测
- **暂缓原因**：Supabase RLS + PostgreSQL 事务已保证数据一致性，当前业务场景中并发冲突几乎不出现
- **启动条件**：多人协同编辑场景出现后

### 13. "CEO Agent" 架构重构
- **建议来源**：IanCompany_V2 架构启发 §1.1
- **内容**：将 router→WBS→orchestrator 重构为显式 CEO Agent 模式
- **暂缓原因**：当前的 router.py（意图分类）→ nodes_wbs.py（WBS拆解）→ nodes_orchestrator.py（10角色编排）本质上已是 CEO 模式，改名不增加实际价值
- **评估**：如果未来需要对外展示架构优势时可以做命名层面的重构
