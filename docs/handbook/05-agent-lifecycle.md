# Agent 生命周期

## 请求路径

1. API 验证身份、组织、配额和输入安全。
2. Router 识别场景与复杂度；简单请求走快速路径。
3. Context 只注入与当前用户、组织、页面和任务相关的证据。
4. Planner 生成受约束计划；Tool Catalog 限定可见工具。
5. Execute 执行权限、参数、幂等、熔断和 HITL 检查。
6. Reflect/Critic 只在有收益且未超预算时运行。
7. Respond 通过 SSE 输出结论、证据、动作和可恢复状态。
8. Eval/Trace 记录质量、成本、失败归因和人工反馈。

## 精品成果路径

普通问答完成后，用户选择“制作精品成果”才进入独立交付链路：

1. 根据成果类型、客户、仪器谱系和明确选择的文档重新构建检索查询。
2. 只在当前组织的可检索资料中做名称、关键词、向量和关系混合召回，并生成可审计证据包。
3. 规划科学仪器文档结构，生成初稿并检查参数、案例、政策、竞品和外部承诺。
4. 在预算内执行事实核验、反思和定向修复，随后运行结构、语义、格式与安全质量门。
5. 保存成果、质量快照和下载格式；未通过硬门禁的结果保留为审核草稿。
6. 人工复核后记录采用、编辑、赢单或未采用结果，作为受治理的模板改进信号。

这一链路由持久化任务承载。聊天消息只是输入之一，不能直接当作最终文件正文。

## 关键控制

- 默认模型和升级策略在后端网关统一执行。
- 工具失败不能伪装成业务成功；错误需可归因、可重试或可补偿。
- 反思循环受次数、Token、时间和重复检测约束。
- 普通用户看到决策依据，不暴露内部思维链；管理员在 Agent Ops 查看结构化 trace。
- 检索结果必须携带 `document_id`、文档名、片段和证据标识；无法定位来源时不得生成确定性参数或案例。
- 资料入库未完成、证据不足或质量门失败时，应给出可恢复动作，而不是声称“知识库没有文件”。

修改 prompt、context 或 graph 时必须补充回归 case，并说明质量与成本变化。
