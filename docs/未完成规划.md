# 未完成规划 — 长期优化项

> 最后更新: 2026-03-24
> 来源: 9 维度 Agent Harness 审计

## 1. 全链路端到端加密 (E2EE)

**优先级**: 长期
**领域**: 安全/合规

当前状态: 用户 ↔ 服务端通信依赖 TLS，服务端持有明文。对于金融/医疗等高合规场景，需实现端到端加密，确保服务端也无法解密用户对话内容。

### 建议方向
- 客户端生成会话密钥，使用 WebCrypto API 加密消息
- 服务端仅存储密文，解密在客户端完成
- 需要重新设计 RAG/记忆搜索（对密文无法做语义检索）
- 可以考虑同态加密或 Trusted Execution Environment (TEE) 方案

### 前置条件
- 明确合规要求（HIPAA / GDPR / 等保三级）
- 评估对 RAG 和 Agent 工具链的影响

## 2. Agent 可解释性审计日志

**优先级**: 长期
**领域**: 可观测性/合规

当前状态: `agent_traces` 记录了执行步骤，但缺乏因果链——为什么选择了这个工具、为什么生成了这个计划、为什么拒绝了用户请求。

### 建议方向
- 在 `node_plan.py` 和 `node_execute.py` 中记录 LLM 的推理摘要（非完整 prompt，而是结构化决策记录）
- 格式: `{decision, alternatives_considered, reasoning, confidence}`
- 审批/HR/财务等高敏感场景强制记录
- 前端提供 "为什么这样做" 的展开面板

### 前置条件
- 定义哪些场景需要可解释性（审批? 全部?）
- Token 消耗评估（额外的 LLM 调用生成摘要）

## 3. 多 Agent 协作框架

**优先级**: 长期
**领域**: Agent 架构

当前状态: 单 Agent + 工具链模式。复杂任务（如跨部门审批+通知+报告生成）在单 Agent 内通过多轮工具调用完成，容易超时和上下文溢出。

### 建议方向
- Supervisor-Worker 模式: 主 Agent 拆解任务，分派给专业子 Agent
- 子 Agent 类型: CRM Agent、HR Agent、Finance Agent、Document Agent
- 基于 LangGraph 的 multi-agent 编排（已有 `nodes_orchestrator.py` 作为基础）
- 共享状态通过 Redis 或 PostgreSQL 传递

### 前置条件
- 明确哪些场景需要多 Agent（当前单 Agent 是否已到瓶颈）
- 评估延迟和成本（多 Agent = 多 LLM 调用）

## 4. 插件市场与第三方工具沙箱

**优先级**: 长期
**领域**: 平台化/安全

当前状态: 工具是硬编码在 `app/tools/` 中的，新增工具需要改代码+部署。`installed_plugins` 表已存在但未实际使用。

### 建议方向
- 插件 SDK: 定义工具的标准接口（OpenAPI spec + manifest.json）
- 沙箱执行: 第三方工具在 Docker/Firecracker 沙箱中运行，限制网络和文件系统
- 权限模型: 插件声明所需权限（读客户数据、写审批等），用户授权
- 市场: 插件发布、审核、版本管理

### 前置条件
- 确定是否有第三方开发者需求
- 安全审计框架（沙箱逃逸防护）

## 5. 离线/弱网 Agent 降级策略

**优先级**: 长期
**领域**: 可用性/移动端

当前状态: Agent 完全依赖在线 LLM API。移动端弱网环境下，SSE 流中断导致用户体验差。

### 建议方向
- 本地缓存常用查询结果（语义缓存已有 `semantic_cache` 表）
- 轻量级本地模型（如 Phi-3-mini）处理简单查询
- 离线队列: 弱网时将请求入队，恢复后自动执行
- PWA 支持: Service Worker 缓存静态资源和常用 API 响应

### 前置条件
- 明确移动端使用场景和占比
- 评估本地模型的硬件要求
